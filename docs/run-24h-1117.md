The user (2026-11-16 ~23:50): "work nonstop for 24 hours you have the console all to yourself do all 30 codgen ideas

## Findings that came first

- **Renut's record mutex on the frame chain.** The console's sampled stacks over the racing stretch (the 15 ms build,
  two races, reports 9-20; scratchpad wait_census.py): every frame-job worker (JQ0, JQ1, JQ2, JQ4) spends 8.6-9.7 % of
  its time waiting in `pthread_mutex_lock` from Renut's NewOp, ~1 % more in its unlock and ~1 % from the
  BeginCommandBuffer hook: ~11 % of each worker. Game Master waits 20.4 % of its time for the frame jobs (yields in
  8227CCE8 / 822862B0), which those lock waits stretch. NewOp's lock-free memo was invalidated globally: one generation
  bumped by every BeginRecording / ReleaseCommandBuffer / new buffer anywhere, and one pending-vertices count for all
  devices. Fixed: a hashed generation per command buffer and a pending count per device
  (`blur_renut_record_memo_local`, on).
- **The hooks' first steps, the same way.** Game Master waits 3.3 % of its racing time on the delta chain's lock in
  QueueDraw. Every D3D hook first calls FlushDeferredVertices (and it FlushRecordedVertices), which took the chain's
  lock and the deferred map's (or the record mutex) whenever any device had a Begin*Vertices draw waiting, though they
  only flush their own device's. Fixed: hashed per-device counts kept with the map and the pending list
  (`blur_renut_flush_fast_local`, on; 8c635efb, the second pass of batch 1).
- **Game Master's per-draw costs on the host side** (scratchpad host_top.py, the same profiles): 1.2 % of its time in
  `pthread_rwlock_unlock` in the BeginVertices hook (InPlaceShaderEntry's shared lock, twice a narrowed capture, on a
  map that changes only when a shader is registered or destroyed), and 1.9 % in newlib's `memalign`, 0.8 % of it a new
  12.9 KB Run at every RunCommandBuffer. Fixed (0bbb3cbc, batch 1's use build): a per-thread memo of the in-place
  shaders checked against a generation bumped at every change (`blur_renut_in_place_memo`), the thread's last
  vertices scratch per device (exact: never changes once made), and a pool of up to 64 runs (`blur_renut_run_pool`).
- **The late-input delay costs nothing in races.** Counted over whole sessions, Game Master's `nanosleep` in
  rex::input::InputSystem::GetState (the late-input delay, `banjo_late_input`) looked like 11.7 % of its time; the
  game's own log shows the delay at 4.7-11.8 ms only in the menus and 0.0 ms through every racing stretch. The A/B
  (late input off) in the night's sequence checks it on the race.
- **The machine waits on memory.** tools/codegen_census.py samples (the 15 ms build): 56.5 % of all console samples sit
  on loads (14.4 % on guest loads through the 32-bit index), stores 15 %, integer work 15 %, float / vector 10 %, byte
  swaps 0.6 %, system instructions (flush-mode switches) 0.9 %. What is left to win is in waits (locks, sleeps) and in
  cache misses (pointer chases), not in the generated code's instruction count: the codegen ideas that remove
  instructions (#228, #229, #213, #234, #235) were measured or reasoned out by that.
- **Guest memory in large blocks (#189 of the earlier list):** already in the base (guest_memory_switch.cpp commits
  2 MB-aligned chunks so Horizon maps them with block descriptors).
- **The indirect-call dispatch table misses.** 0.4-0.5 % of all console samples (1.6-3.3 % of JQ Worker 3's) sit on the
  one load of REX_LOOKUP_FUNC (a 20 MB table). CG-08 built: a one-entry cache per call site.

**The PC census of the inexact audio** (census_1117, 480 s, the new keys at 0.001): of 10.7 M voice steps, 7.6 M (71 %)
are already under Blur's own floor (1e-4) and take the game's inaudible path (their rows zeroed, the source only
advanced); the -60 dB floor adds 48,000 (0.45 %). The mixer's gains: 13.5 M zero (skipped as before), 1.9 M exactly 1,
22.1 M others, of which only 114,000 within 1e-5 of 1 and 150,000 under 2^-16; 6.4 M ramps. The tolerances' wider
bound buys little; what the census does show is that most voices are silent: #197 (the node loop not mixing a child
whose rows are all zero) is the audio saving of the batch, with #197b (their effect stages).

**The audio dumps** (PC, 120 s each from 150 s into the race; scratchpad audio_dump_compare.py / audio_silences.py):
the new values against the shipped ones: no NaN, no clipping, overall RMS -21.8 / -22.0 dBFS against -22.3 / -22.2, the
octave bands within the races' own variation. The silences are the PC's load (the instrumented build compiled during
both runs): 2 stretches in the new run, 32 in the reference.

**The PC guard race** (guard_1117, batch 1's copies, every one compared with the original at each call): 1934 of 1936
native copies on (the other two, bulk 8230B338 and 8249CB30, are off in the toml: their copies write r12 back and
the originals do not), 1901 of 1903 bulk copies reached; 148 M calls compared, 0 differences (3,475 differed once and not
when repeated: another thread's inputs). 82953D90 (the copy native, `exact=r3`): 5.0 M calls, 0 differences.

**A toml mistake, caught before the training.** Batch 1's tomls had their four new keys appended after `[input_p2]`.
Rex's loader (sdk/src/core/cvar.cpp, ApplyTomlTable) names a table's keys `<table>_<key>`, so they were
`input_p2_audio_nx_voice_floor` and so on, matched no cvar and were dropped silently: the batch would have trained and
raced with all four at their defaults (off). Moved above `[input_p1]` at 01:48 (scratchpad fix_b1_tomls.py, which
also checks that no other key is left under a table); every other toml of the run (dist/switch/blur-nx/configs, the
A/B folders, 33 in all) was scanned and had none there.

**The first instrumented build stopped at startup** (02:02, training scene 1): ESR EC 0x18, a trapped system
register access, on `mrs x3, cntvct_el0` in RexSiteMiss (CG-08's miss path, which picks 1 miss in 16 to replace a
full site word). Horizon lets EL0 read the physical counter (cntpct_el0, libnx's armGetSystemTick) but not the virtual
one. The block is Switch-only, so the PC guard race could not see it. Fixed in tools/indirect_calls.py (5a6bc972) and
in batch 1's generated pch (its block was exactly the pass's bbd8b0e6 text; scratchpad patch_pch_cg08.py checks that,
then writes the pass's current text, which also brings 161f9787's hit test). The instrumented build was rebuilt from
02:09 (every generated object: the pch changed); the settling races ran meanwhile.
